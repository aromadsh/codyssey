# 절대경로와 상대경로

## 1. 절대경로란?

절대경로(Absolute Path)는 파일 시스템의 **최상위 위치인 루트(Root)**부터 원하는 파일이나 폴더까지의 전체 경로를 작성하는 방식입니다.

### 특징

- 현재 작업 중인 위치와 관계없이 항상 같은 파일을 가리킵니다.
- 파일이나 폴더의 위치를 명확하게 나타낼 수 있습니다.
- 운영체제에 따라 경로 표현 방식이 다릅니다.

### 비유

절대경로는 다음과 같은 전체 주소와 비슷합니다.

> 대한민국 서울특별시 강남구 테헤란로 123번지

현재 어디에 있든 전체 주소를 알면 같은 장소를 찾을 수 있습니다.

### 예시

#### Windows

```text
C:\Users\Student\Documents\study.txt
```

#### Linux 또는 macOS

```text
/home/student/documents/study.txt
```

#### 웹의 절대 URL

```text
https://www.example.com/images/logo.png
```

---

## 2. 상대경로란?

상대경로(Relative Path)는 **현재 작업 중인 디렉터리(Current Directory)**를 기준으로 파일이나 폴더의 위치를 표현하는 방식입니다.

### 특징

- 현재 위치에 따라 경로의 의미가 달라집니다.
- 프로젝트 내부의 파일을 연결할 때 자주 사용합니다.
- 프로젝트 폴더를 다른 위치로 옮겨도 내부 구조가 같으면 경로를 그대로 사용할 수 있습니다.

### 비유

상대경로는 다음과 같은 길 안내와 비슷합니다.

> 여기서 오른쪽으로 이동한 뒤 두 번째 건물로 가세요.

현재 위치가 바뀌면 길 안내도 달라질 수 있습니다.

### 주요 기호

| 기호 | 의미 |
|---|---|
| `.` | 현재 디렉터리 |
| `..` | 현재 디렉터리의 상위 디렉터리 |
| `/` | Linux, macOS, 웹에서 사용하는 경로 구분 기호 |
| `\` | Windows에서 주로 사용하는 경로 구분 기호 |

### 예시

현재 디렉터리에 있는 `memo.txt` 파일:

```text
./memo.txt
```

상위 디렉터리의 `images` 폴더에 있는 `cat.jpg` 파일:

```text
../images/cat.jpg
```

---

## 3. 절대경로와 상대경로 비교

현재 위치가 다음과 같다고 가정해 봅시다.

```text
C:\Project\src
```

찾으려는 파일의 위치는 다음과 같습니다.

```text
C:\Project\data\test.txt
```

| 구분 | 작성 예시 | 설명 |
|---|---|---|
| 절대경로 | `C:\Project\data\test.txt` | 드라이브의 시작 위치부터 전체 경로를 작성 |
| 상대경로 | `..\data\test.txt` | `src`의 상위 폴더로 이동한 후 `data` 폴더에 접근 |

상대경로의 이동 과정을 표현하면 다음과 같습니다.

```text
C:\Project\src
        ↓ ..
C:\Project
        ↓ data
C:\Project\data
        ↓ test.txt
C:\Project\data\test.txt
```

---

## 4. 언제 어떤 경로를 사용할까?

### 절대경로를 사용하는 경우

- 위치가 고정된 시스템 파일을 지정할 때
- 외부 웹사이트의 URL을 작성할 때
- 현재 작업 위치와 관계없이 같은 파일에 접근해야 할 때

### 상대경로를 사용하는 경우

- 프로젝트 내부 파일을 참조할 때
- HTML, CSS, JavaScript 파일을 서로 연결할 때
- 프로젝트를 다른 컴퓨터나 서버로 옮길 때
- 여러 개발자가 같은 프로젝트 구조로 협업할 때

---

## 핵심 요약

- **절대경로:** 루트부터 목적지까지 전체 경로를 작성합니다.
- **상대경로:** 현재 위치를 기준으로 목적지까지의 경로를 작성합니다.
- `.`은 현재 디렉터리입니다.
- `..`은 상위 디렉터리입니다.
2. 파일 권한의 의미와 755, 644 해석법
# Linux 파일 권한과 숫자 표기법

Linux와 Unix 계열 운영체제에서는 파일과 디렉터리에 대해 **누가 어떤 작업을 할 수 있는지** 권한을 설정합니다.

파일 권한은 일반적으로 다음 세 가지 기호로 표현합니다.

- `r`: 읽기
- `w`: 쓰기
- `x`: 실행

---

## 1. `r`, `w`, `x`의 의미

| 권한 | 영문 | 파일에서의 의미 | 디렉터리에서의 의미 |
|---|---|---|---|
| `r` | Read | 파일 내용 읽기 | 디렉터리 내부 목록 확인 |
| `w` | Write | 파일 내용 수정 | 내부에 파일 생성, 삭제, 이름 변경 |
| `x` | Execute | 파일 실행 | 디렉터리 내부로 이동하고 항목에 접근 |
| `-` | 없음 | 해당 권한 없음 | 해당 권한 없음 |

> 파일 삭제 권한은 파일 자체의 `w` 권한보다 파일이 들어 있는 디렉터리의 `w`, `x` 권한에 영향을 받습니다.

---

## 2. 권한을 숫자로 표현하는 규칙

각 권한에는 다음과 같은 숫자가 지정되어 있습니다.

| 권한 | 숫자 |
|---|---:|
| 읽기 `r` | 4 |
| 쓰기 `w` | 2 |
| 실행 `x` | 1 |
| 권한 없음 `-` | 0 |

필요한 권한의 숫자를 더하면 하나의 숫자로 표현할 수 있습니다.

| 숫자 | 계산 | 기호 |
|---:|---|---|
| 7 | 4 + 2 + 1 | `rwx` |
| 6 | 4 + 2 | `rw-` |
| 5 | 4 + 1 | `r-x` |
| 4 | 4 | `r--` |
| 3 | 2 + 1 | `-wx` |
| 2 | 2 | `-w-` |
| 1 | 1 | `--x` |
| 0 | 0 | `---` |

---

## 3. 세 자리 숫자의 의미

`755`, `644`처럼 숫자가 세 자리인 이유는 권한을 적용받는 대상이 세 그룹으로 나뉘기 때문입니다.

| 위치 | 대상 | 설명 |
|---|---|---|
| 첫 번째 숫자 | 소유자(User) | 파일이나 디렉터리의 소유자 |
| 두 번째 숫자 | 그룹(Group) | 해당 파일의 그룹에 속한 사용자 |
| 세 번째 숫자 | 기타 사용자(Others) | 소유자와 그룹을 제외한 사용자 |

다음과 같은 구조입니다.

```text
755
││└─ 기타 사용자 권한
│└── 그룹 권한
└─── 소유자 권한
```

---

## 4. `755` 권한 해석

```text
755
```

### 소유자 권한: `7`

```text
4 + 2 + 1 = 7
r + w + x = rwx
```

소유자는 읽기, 쓰기, 실행을 모두 할 수 있습니다.

### 그룹 권한: `5`

```text
4 + 1 = 5
r + x = r-x
```

그룹 사용자는 읽기와 실행을 할 수 있지만 수정은 할 수 없습니다.

### 기타 사용자 권한: `5`

```text
4 + 1 = 5
r + x = r-x
```

기타 사용자도 읽기와 실행을 할 수 있지만 수정은 할 수 없습니다.

### 기호 표기

```text
rwxr-xr-x
```

### 주요 용도

- 실행 스크립트
- 프로그램 파일
- 웹 서버의 공개 디렉터리
- 다른 사용자가 접근해야 하는 디렉터리

---

## 5. `644` 권한 해석

```text
644
```

### 소유자 권한: `6`

```text
4 + 2 = 6
r + w = rw-
```

소유자는 파일을 읽고 수정할 수 있습니다.

### 그룹 권한: `4`

```text
4 = r--
```

그룹 사용자는 파일을 읽을 수만 있습니다.

### 기타 사용자 권한: `4`

```text
4 = r--
```

기타 사용자도 파일을 읽을 수만 있습니다.

### 기호 표기

```text
rw-r--r--
```

### 주요 용도

- 일반 문서 파일
- 소스 코드 파일
- 설정 파일
- HTML, CSS, JavaScript 파일

---

## 6. 권한 확인하기

파일과 디렉터리의 권한은 다음 명령어로 확인할 수 있습니다.

```bash
ls -l
```

실행 결과 예시:

```text
-rwxr-xr-x 1 user group 1200 Jul 30 10:00 script.sh
```

각 부분의 의미는 다음과 같습니다.

```text
- rwx r-x r-x
│ │   │   └─ 기타 사용자 권한
│ │   └───── 그룹 권한
│ └───────── 소유자 권한
└─────────── 파일 종류
```

맨 앞 문자의 의미:

| 문자 | 의미 |
|---|---|
| `-` | 일반 파일 |
| `d` | 디렉터리 |
| `l` | 심볼릭 링크 |

---

## 7. 권한 변경하기

`chmod` 명령어를 사용하면 권한을 변경할 수 있습니다.

### 파일을 `755`로 변경

```bash
chmod 755 script.sh
```

### 파일을 `644`로 변경

```bash
chmod 644 config.txt
```

### 소유자에게 실행 권한 추가

```bash
chmod u+x script.sh
```

여기서 `u`는 소유자(User), `+x`는 실행 권한 추가를 의미합니다.

---

## 핵심 요약

- `r`은 읽기 권한이며 숫자 `4`입니다.
- `w`는 쓰기 권한이며 숫자 `2`입니다.
- `x`는 실행 권한이며 숫자 `1`입니다.
- 첫 번째 숫자는 소유자 권한입니다.
- 두 번째 숫자는 그룹 권한입니다.
- 세 번째 숫자는 기타 사용자 권한입니다.
- `755`는 `rwxr-xr-x`입니다.
- `644`는 `rw-r--r--`입니다.
3. Dockerfile을 기반으로 커스텀 이미지 만들기
# Dockerfile로 커스텀 이미지 만들기

Docker 이미지는 컨테이너를 실행하기 위한 템플릿입니다.

기존 Docker 이미지를 기반으로 필요한 프로그램, 파일, 환경설정 등을 추가하면 자신만의 **커스텀 Docker 이미지**를 만들 수 있습니다.

---

## 1. Dockerfile이란?

`Dockerfile`은 Docker 이미지를 만들기 위한 설계도입니다.

Dockerfile 안에는 다음과 같은 내용이 작성됩니다.

- 어떤 이미지를 기반으로 사용할지
- 어떤 파일을 이미지 안으로 복사할지
- 어떤 패키지를 설치할지
- 컨테이너가 시작될 때 어떤 명령을 실행할지

파일 이름은 일반적으로 확장자 없이 다음과 같이 작성합니다.

```text
Dockerfile
```

---

## 2. 프로젝트 구조 만들기

간단한 Python 애플리케이션을 이미지로 만든다고 가정해 봅시다.

```text
my-project/
├── Dockerfile
├── requirements.txt
└── app.py
```

### `app.py`

```python
from flask import Flask

app = Flask(__name__)

@app.route("/")
def home():
    return "Hello, Docker!"

if __name__ == "__main__":
    app.run(host="0.0.0.0", port=5000)
```

### `requirements.txt`

```text
flask
```

---

## 3. Dockerfile 작성하기

```dockerfile
# 1. 기존 Python 이미지를 베이스 이미지로 사용
FROM python:3.9-slim

# 2. 컨테이너 내부 작업 디렉터리 설정
WORKDIR /app

# 3. 의존성 파일 복사
COPY requirements.txt .

# 4. Python 패키지 설치
RUN pip install --no-cache-dir -r requirements.txt

# 5. 나머지 프로젝트 파일 복사
COPY . .

# 6. 애플리케이션이 사용하는 포트 안내
EXPOSE 5000

# 7. 컨테이너 시작 시 실행할 명령
CMD ["python", "app.py"]
```

---

## 4. Dockerfile 주요 명령어

| 명령어 | 설명 |
|---|---|
| `FROM` | 기반으로 사용할 기존 이미지 지정 |
| `WORKDIR` | 컨테이너 내부의 작업 디렉터리 지정 |
| `COPY` | 호스트의 파일을 이미지 내부로 복사 |
| `RUN` | 이미지 빌드 과정에서 명령 실행 |
| `EXPOSE` | 애플리케이션이 사용할 포트를 문서화 |
| `CMD` | 컨테이너 시작 시 실행할 기본 명령 지정 |

---

## 5. 이미지 빌드하기

Dockerfile이 있는 디렉터리에서 다음 명령어를 실행합니다.

```bash
docker build -t my-custom-app:1.0 .
```

각 부분의 의미는 다음과 같습니다.

| 항목 | 의미 |
|---|---|
| `docker build` | Docker 이미지 빌드 |
| `-t` | 이미지 이름과 태그 지정 |
| `my-custom-app` | 이미지 이름 |
| `1.0` | 이미지 태그 또는 버전 |
| `.` | 현재 디렉터리를 빌드 컨텍스트로 사용 |

마지막의 `.`을 빠뜨리지 않도록 주의해야 합니다.

---

## 6. 생성된 이미지 확인하기

다음 명령어로 이미지 목록을 확인할 수 있습니다.

```bash
docker images
```

또는 다음 명령어를 사용할 수 있습니다.

```bash
docker image ls
```

출력 예시:

```text
REPOSITORY      TAG       IMAGE ID       CREATED          SIZE
my-custom-app   1.0       abc123def456   10 seconds ago   130MB
```

---

## 7. 커스텀 이미지 실행하기

```bash
docker run -d -p 5000:5000 --name my-app my-custom-app:1.0
```

각 옵션의 의미는 다음과 같습니다.

| 옵션 | 의미 |
|---|---|
| `-d` | 컨테이너를 백그라운드에서 실행 |
| `-p 5000:5000` | 호스트의 5000번 포트와 컨테이너의 5000번 포트 연결 |
| `--name my-app` | 컨테이너 이름을 `my-app`으로 지정 |
| `my-custom-app:1.0` | 실행할 이미지와 태그 |

브라우저에서 다음 주소로 접속합니다.

```text
http://localhost:5000
```

정상적으로 실행되었다면 다음 문장이 표시됩니다.

```text
Hello, Docker!
```

## 8. 실행 중인 컨테이너 확인하기

```bash
docker ps
```

중지된 컨테이너까지 모두 확인하려면 다음 명령어를 사용합니다.

```bash

```

## 10. Docker 레이어와 캐시

Dockerfile의 명령어는 이미지에 여러 개의 레이어를 만듭니다.

Docker는 이전 빌드 결과를 캐시하므로, 자주 변경되지 않는 작업을 Dockerfile의 위쪽에 배치하는 것이 좋습니다.

다음과 같은 순서를 권장합니다.

```dockerfile
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
```

이렇게 작성하면 소스 코드가 변경되더라도 `requirements.txt`가 변경되지 않은 경우 패키지 설치 단계의 캐시를 재사용할 수 있습니다.

---

## 11. `.dockerignore` 사용하기

빌드에 필요하지 않은 파일은 `.dockerignore`에 작성할 수 있습니다.

### `.dockerignore` 예시

```text
.git
.gitignore
__pycache__
*.pyc
.env
venv
```

이 파일을 사용하면 불필요한 파일이 이미지에 포함되는 것을 방지하고 빌드 속도와 이미지 크기를 개선할 수 있습니다.

## 전체 과정 요약

```text
Dockerfile 작성
      ↓
docker build
      ↓
Docker 이미지 생성
      ↓
docker run
      ↓
컨테이너 실행
```

주요 명령어:

```bash
docker build -t my-custom-app:1.0 .
docker image ls
docker run -d -p 5000:5000 my-custom-app:1.0
docker ps
```
4. Docker 포트 매핑이 필요한 이유
# Docker 포트 매핑이 필요한 이유

포트 매핑(Port Mapping)은 **호스트 컴퓨터의 포트와 Docker 컨테이너 내부의 포트를 연결하는 기능**입니다.

컨테이너 내부에서 웹 서버가 실행되고 있더라도 포트가 외부에 공개되지 않으면 호스트의 브라우저나 외부 컴퓨터에서 해당 서비스에 접근하기 어렵습니다.

---

## 1. 호스트와 컨테이너

Docker 환경에서는 다음 두 공간을 구분해야 합니다.

### 호스트

Docker를 실행하고 있는 실제 컴퓨터입니다.

예를 들면 다음과 같습니다.

- 개인용 노트북
- 데스크톱 컴퓨터
- 클라우드 서버
- 가상 머신

### 컨테이너

Docker가 독립적으로 실행하는 격리된 환경입니다.

컨테이너는 자체적인 프로세스와 네트워크 환경을 가질 수 있습니다.

---

## 2. 포트 매핑이 필요한 이유

컨테이너 안에서 웹 서버가 `80`번 포트를 사용한다고 가정해 봅시다.

컨테이너 내부에서는 다음 주소로 서비스가 실행됩니다.

```text
컨테이너 내부의 80번 포트
```

하지만 호스트 브라우저에서 다음 주소에 접속한다고 해서 자동으로 컨테이너의 서비스에 연결되는 것은 아닙니다.

```text
http://localhost:80
```

`localhost`는 현재 접속하고 있는 호스트 컴퓨터를 의미하기 때문입니다.

따라서 호스트로 들어온 요청을 컨테이너 내부로 전달할 규칙이 필요합니다. 이 규칙이 포트 매핑입니다.

---

## 3. 포트 매핑 구조

포트 매핑을 사용하면 요청이 다음과 같이 전달됩니다.

```text
사용자 또는 브라우저
        ↓
호스트 컴퓨터의 포트
        ↓
Docker 포트 매핑
        ↓
컨테이너 내부의 포트
        ↓
컨테이너 내부 애플리케이션
```

---

## 4. 포트 매핑 명령어

다음 명령어는 Nginx 컨테이너를 실행하면서 포트를 연결합니다.

```bash
docker run -p 8080:80 nginx
```

`-p` 옵션은 다음 형식으로 작성합니다.

```text
-p 호스트포트:컨테이너포트
```

따라서 다음 설정은 다음과 같이 해석합니다.

```text
8080:80
```

| 포트 | 의미 |
|---|---|
| `8080` | 호스트 컴퓨터에서 사용할 포트 |
| `80` | 컨테이너 내부 웹 서버가 사용하는 포트 |

브라우저에서는 다음 주소로 접속합니다.

```text
http://localhost:8080
```

요청 전달 과정:

```text
localhost:8080
        ↓
컨테이너의 80번 포트
        ↓
Nginx 웹 서버
```

---

## 5. 쉬운 비유

포트 매핑은 아파트의 공동 현관과 비슷합니다.

- 호스트 컴퓨터: 아파트 건물
- 컨테이너: 개별 세대
- 호스트 포트: 공동 현관의 호출 번호
- 컨테이너 포트: 세대 내부에서 서비스가 사용하는 번호

외부 사람이 개별 세대에 접근하려면 공동 현관에서 어느 세대로 연결할지 정해진 규칙이 필요합니다.

포트 매핑은 다음과 같은 연결 규칙입니다.

> 호스트의 8080번으로 들어온 요청을 컨테이너의 80번으로 전달한다.

---

## 6. 여러 컨테이너 실행하기

컨테이너 내부에서는 모두 `80`번 포트를 사용하더라도 호스트 포트를 다르게 지정하면 여러 컨테이너를 동시에 실행할 수 있습니다.

```bash
docker run -d -p 8081:80 --name web1 nginx
docker run -d -p 8082:80 --name web2 nginx
```

첫 번째 컨테이너 접속 주소:

```text
http://localhost:8081
```

두 번째 컨테이너 접속 주소:

```text
http://localhost:8082
```

연결 구조:

```text
호스트 8081 → web1 컨테이너 80
호스트 8082 → web2 컨테이너 80
```

호스트에서는 같은 포트를 두 개의 컨테이너가 동시에 사용할 수 없으므로 서로 다른 호스트 포트를 지정해야 합니다.

---

## 7. 특정 IP에만 포트 공개하기

다음과 같이 실행하면 호스트의 모든 네트워크 인터페이스에 포트가 공개될 수 있습니다.

```bash
docker run -p 8080:80 nginx
```

로컬 컴퓨터에서만 접근하도록 제한하려면 다음과 같이 작성할 수 있습니다.

```bash
docker run -p 127.0.0.1:8080:80 nginx
```

이 경우 같은 컴퓨터에서는 접근할 수 있지만 외부 컴퓨터에서는 직접 접근할 수 없습니다.

---

## 8. `EXPOSE`와 `-p`의 차이

Dockerfile에는 다음과 같이 `EXPOSE`를 작성할 수 있습니다.

```dockerfile
EXPOSE 80
```

`EXPOSE`는 컨테이너의 애플리케이션이 어떤 포트를 사용할 예정인지 알려주는 문서화 역할을 합니다.

하지만 `EXPOSE`만 작성한다고 호스트 포트와 자동으로 연결되는 것은 아닙니다.

실제로 포트를 연결하려면 컨테이너를 실행할 때 `-p` 옵션을 사용해야 합니다.

```bash
docker run -p 8080:80 nginx
```

| 구분 | 역할 |
|---|---|
| `EXPOSE 80` | 이미지가 사용하는 포트를 안내 |
| `-p 8080:80` | 호스트와 컨테이너 포트를 실제로 연결 |

---

## 9. 포트 매핑이 필요하지 않은 경우

모든 컨테이너에 포트 매핑이 필요한 것은 아닙니다.

다음과 같은 경우에는 외부 포트 공개가 필요하지 않을 수 있습니다.

- 일회성 명령만 실행하는 컨테이너
- 배치 작업 컨테이너
- 외부 요청을 받지 않는 백그라운드 작업
- 같은 Docker 네트워크의 다른 컨테이너만 접근하는 내부 서비스

예를 들어 웹 서버 컨테이너와 데이터베이스 컨테이너가 같은 Docker 네트워크에 있다면 웹 서버는 데이터베이스의 컨테이너 포트로 직접 접근할 수 있습니다.

데이터베이스를 호스트나 외부에 공개할 필요가 없다면 포트 매핑을 생략할 수 있습니다.

---

## 핵심 요약

- 컨테이너는 호스트와 분리된 네트워크 환경에서 실행됩니다.
- 포트 매핑은 호스트의 포트와 컨테이너의 포트를 연결합니다.
- `-p` 옵션은 `호스트포트:컨테이너포트` 순서로 작성합니다.
- `docker run -p 8080:80 nginx`는 호스트의 `8080`을 컨테이너의 `80`에 연결합니다.
- 여러 컨테이너를 실행할 때는 호스트 포트를 서로 다르게 지정해야 합니다.
- `EXPOSE`는 포트를 문서화하지만 실제 포트 매핑을 만들지는 않습니다.
5. Docker 볼륨과 영속 데이터
# Docker 볼륨과 영속 데이터

Docker 컨테이너 내부에 저장된 데이터는 컨테이너의 생명주기에 영향을 받습니다.

컨테이너를 삭제하면 컨테이너의 쓰기 가능 계층에 저장된 데이터도 함께 사라질 수 있습니다.

데이터를 컨테이너와 분리하여 안전하게 보관하기 위해 사용하는 기능이 **Docker 볼륨(Volume)**입니다.

---

## 1. 볼륨이 필요한 이유

컨테이너는 필요할 때 생성하고 삭제하기 쉽도록 설계되어 있습니다.

그러나 다음과 같은 데이터는 컨테이너를 삭제하더라도 유지되어야 합니다.

- 데이터베이스 데이터
- 사용자가 업로드한 이미지
- 애플리케이션 로그
- 설정 파일
- 작업 결과물
- 백업 파일

볼륨을 사용하지 않고 컨테이너 내부에만 데이터를 저장하면 컨테이너 삭제 시 중요한 데이터가 함께 사라질 수 있습니다.

---

## 2. 컨테이너와 데이터 분리

볼륨을 사용하지 않는 경우:

```text
컨테이너
├── 애플리케이션
└── 데이터
```

컨테이너를 삭제하면 내부 데이터도 함께 사라질 수 있습니다.

볼륨을 사용하는 경우:

```text
컨테이너
└── 애플리케이션
       │
       └── Docker 볼륨
             └── 데이터
```

컨테이너를 삭제하고 새로 생성해도 같은 볼륨을 다시 연결하면 기존 데이터를 사용할 수 있습니다.

---

## 3. Named Volume

Named Volume은 Docker가 직접 관리하는 저장 공간입니다.

먼저 볼륨을 생성합니다.

```bash
docker volume create my_data
```

생성된 볼륨 목록을 확인합니다.

```bash
docker volume ls
```

볼륨을 컨테이너에 연결합니다.

```bash
docker run -v my_data:/app/data nginx
```

`-v` 옵션은 다음 구조로 사용합니다.

```text
-v 볼륨이름:컨테이너경로
```

위 명령어는 다음과 같은 의미입니다.

```text
my_data 볼륨
      ↓
컨테이너의 /app/data 디렉터리에 연결
```

---

## 4. 볼륨 정보 확인하기

볼륨의 상세 정보를 확인하려면 다음 명령어를 사용합니다.

```bash
docker volume inspect my_data
```

볼륨을 삭제하려면 다음 명령어를 사용합니다.

```bash
docker volume rm my_data
```

사용하지 않는 볼륨을 한꺼번에 정리하려면 다음 명령어를 사용할 수 있습니다.

```bash
docker volume prune
```

> 볼륨을 삭제하면 저장된 데이터도 함께 삭제될 수 있으므로 주의해야 합니다.

---

## 5. Bind Mount

Bind Mount는 호스트 컴퓨터의 특정 파일이나 디렉터리를 컨테이너 내부에 직접 연결하는 방식입니다.

Linux 또는 macOS 예시:

```bash
docker run -v /Users/me/project:/app nginx
```

현재 디렉터리를 연결하는 예시:

```bash
docker run -v "$(pwd)":/app nginx
```

Windows PowerShell 예시:

```powershell
docker run -v ${PWD}:/app nginx
```

구조는 다음과 같습니다.

```text
-v 호스트경로:컨테이너경로
```

예시:

```text
/Users/me/project:/app
```

| 위치 | 의미 |
|---|---|
| `/Users/me/project` | 호스트 컴퓨터의 디렉터리 |
| `/app` | 컨테이너 내부에서 연결될 디렉터리 |

호스트에서 파일을 수정하면 컨테이너 내부에도 변경 사항이 바로 반영됩니다.

따라서 Bind Mount는 개발 환경에서 소스 코드를 공유할 때 자주 사용합니다.

---

## 6. `-v` 옵션 읽는 방법

`-v` 옵션은 기본적으로 왼쪽과 오른쪽으로 나누어 읽습니다.

```text
-v 왼쪽:오른쪽
```

| 위치 | 의미 |
|---|---|
| 왼쪽 | 호스트 경로 또는 Docker 볼륨 이름 |
| 오른쪽 | 컨테이너 내부 경로 |

Named Volume 예시:

```bash
docker run -v my_data:/var/lib/mysql mysql
```

Bind Mount 예시:

```bash
docker run -v /home/user/project:/app nginx
```

---

## 7. 읽기 전용 마운트

컨테이너가 연결된 데이터를 읽을 수만 있고 수정하지 못하게 하려면 `ro` 옵션을 추가합니다.

```bash
docker run -v /host/config:/app/config:ro nginx
```

`ro`는 `read-only`를 의미합니다.

연결 구조:

```text
호스트의 /host/config
        ↓ 읽기 전용
컨테이너의 /app/config
```

컨테이너는 파일을 읽을 수 있지만 수정할 수 없습니다.

---

## 8. Named Volume과 Bind Mount 비교

| 구분 | Named Volume | Bind Mount |
|---|---|---|
| 관리 주체 | Docker | 사용자 |
| 왼쪽 값 | 볼륨 이름 | 호스트의 실제 경로 |
| 주요 용도 | 데이터베이스, 운영 데이터 | 개발 소스 코드, 설정 파일 |
| 호스트 경로 의존성 | 낮음 | 높음 |
| Docker 관리 편의성 | 높음 | 상대적으로 낮음 |
| 호스트에서 파일 확인 | 상대적으로 불편 | 쉬움 |

---

## 9. MySQL에서 볼륨 사용하기

MySQL 컨테이너는 일반적으로 `/var/lib/mysql` 디렉터리에 데이터를 저장합니다.

Named Volume을 연결하는 예시:

```bash
docker run -d \
  --name mysql-db \
  -e MYSQL_ROOT_PASSWORD=1234 \
  -v mysql_data:/var/lib/mysql \
  mysql
```

각 옵션의 의미는 다음과 같습니다.

| 옵션 | 의미 |
|---|---|
| `-d` | 백그라운드 실행 |
| `--name mysql-db` | 컨테이너 이름 지정 |
| `-e MYSQL_ROOT_PASSWORD=1234` | 환경변수 설정 |
| `-v mysql_data:/var/lib/mysql` | MySQL 데이터 디렉터리에 볼륨 연결 |
| `mysql` | 사용할 이미지 |

컨테이너를 삭제하더라도 `mysql_data` 볼륨을 삭제하지 않았다면 데이터는 남아 있습니다.

새 컨테이너에 같은 볼륨을 연결하면 기존 데이터를 다시 사용할 수 있습니다.

---

## 10. `--mount` 방식

Docker에서는 `-v` 외에도 `--mount` 옵션을 사용할 수 있습니다.

Named Volume 예시:

```bash
docker run \
  --mount type=volume,source=my_data,target=/app/data \
  nginx
```

Bind Mount 예시:

```bash
docker run \
  --mount type=bind,source=/home/user/project,target=/app \
  nginx
```

`--mount`는 설정 항목이 명확하게 표시되기 때문에 복잡한 설정에서 읽기 쉽다는 장점이 있습니다.

---

## 핵심 요약

- 컨테이너 내부 데이터는 컨테이너 삭제 시 사라질 수 있습니다.
- 볼륨은 컨테이너와 데이터의 생명주기를 분리합니다.
- Named Volume은 Docker가 관리합니다.
- Bind Mount는 호스트의 실제 경로를 컨테이너에 연결합니다.
- `-v` 옵션은 `왼쪽:오른쪽`으로 읽습니다.
- 왼쪽에는 볼륨 이름이나 호스트 경로를 작성합니다.
- 오른쪽에는 컨테이너 내부 경로를 작성합니다.
- 데이터베이스를 실행할 때는 일반적으로 볼륨 사용이 권장됩니다.

# Git과 GitHub의 역할 차이

Git과 GitHub은 함께 사용되는 경우가 많지만 서로 다른 역할을 합니다.

간단히 구분하면 다음과 같습니다.

- **Git:** 로컬 컴퓨터에서 파일의 변경 이력을 관리하는 도구
- **GitHub:** Git 저장소를 인터넷에 저장하고 다른 사람과 협업하는 플랫폼

---

## 1. Git이란?

Git은 컴퓨터에 설치하여 사용하는 **분산 버전 관리 시스템**입니다.

파일이 언제, 어떻게 변경되었는지 기록하고 필요할 때 이전 상태로 돌아갈 수 있도록 도와줍니다.

### Git의 주요 역할

- 파일 변경 이력 관리
- 작업 내용을 커밋으로 저장
- 이전 버전으로 복구
- 브랜치를 사용한 독립적인 작업
- 여러 작업 내용 병합
- 변경 내용 비교

### 특징

- 인터넷 연결 없이도 사용할 수 있습니다.
- 작업 기록이 로컬 컴퓨터에 저장됩니다.
- GitHub 계정이 없어도 사용할 수 있습니다.
- 소스 코드뿐만 아니라 일반 문서도 관리할 수 있습니다.

---

## 2. Git의 주요 개념

### 저장소

Git이 파일 변경 이력을 관리하는 프로젝트 공간입니다.

```bash
git init
```

현재 디렉터리를 Git 저장소로 초기화합니다.

### 스테이징 영역

다음 커밋에 포함할 변경 사항을 선택하는 공간입니다.

```bash
git add .
```

현재 디렉터리의 변경 사항을 스테이징 영역에 추가합니다.

### 커밋

특정 시점의 파일 상태를 하나의 기록으로 저장합니다.

```bash
git commit -m "로그인 기능 추가"
```

### 브랜치

기존 코드에 영향을 주지 않고 독립적으로 작업할 수 있는 작업 흐름입니다.

```bash
git branch feature-login
```

### 병합

다른 브랜치에서 작업한 내용을 현재 브랜치에 합칩니다.

```bash
git merge feature-login
```

---

## 3. GitHub이란?

GitHub은 Git으로 관리하는 저장소를 인터넷에 올리고 공유할 수 있는 **원격 협업 플랫폼**입니다.

GitHub을 사용하면 여러 사람이 같은 프로젝트에 참여하여 코드를 확인하고 수정 사항을 검토할 수 있습니다.

### GitHub의 주요 역할

- 원격 저장소 제공
- 코드 공유와 백업
- 팀 프로젝트 협업
- Pull Request를 통한 코드 리뷰
- Issue를 통한 작업 및 오류 관리
- 프로젝트 문서 관리
- 자동 빌드, 테스트 및 배포

### 특징

- 원격 기능을 사용하려면 인터넷 연결이 필요합니다.
- 웹 브라우저에서 프로젝트 내용을 확인할 수 있습니다.
- 공개 저장소와 비공개 저장소를 만들 수 있습니다.
- 전 세계 개발자와 오픈소스 프로젝트에 참여할 수 있습니다.

---

## 4. Git과 GitHub 비교

| 구분 | Git | GitHub |
|---|---|---|
| 정체 | 버전 관리 소프트웨어 | 원격 저장소 및 협업 플랫폼 |
| 설치 위치 | 로컬 컴퓨터 | 인터넷상의 서버 |
| 주요 목적 | 파일 변경 이력과 버전 관리 | 코드 공유, 백업, 리뷰, 협업 |
| 인터넷 연결 | 기본 기능에는 필요 없음 | 원격 기능 사용 시 필요 |
| 대표 기능 | Commit, Branch, Merge | Pull Request, Issue, Actions |
| 저장 위치 | 로컬 저장소 | 원격 저장소 |
| 대체 도구 또는 서비스 | Mercurial, Subversion 등 | GitLab, Bitbucket 등 |

---

## 5. 쉬운 비유

### Git

Git은 개인 컴퓨터에서 작성하는 **작업 일지 또는 저장 기록**과 같습니다.

작업 중간마다 현재 상태를 기록하고 필요하면 이전 기록으로 돌아갈 수 있습니다.

### GitHub

GitHub은 Git으로 만든 기록을 인터넷에 올려 다른 사람과 공유하는 **온라인 협업 공간**과 같습니다.

팀원이 코드를 확인하고 의견을 남기거나 수정 사항을 제안할 수 있습니다.

---

## 6. Git과 GitHub을 함께 사용하는 과정

일반적인 작업 흐름은 다음과 같습니다.

```text
파일 작성 또는 수정
        ↓
git add
        ↓
git commit
        ↓
git push
        ↓
GitHub 원격 저장소
```

---

## 7. Git 로컬 작업

### Git 저장소 생성

```bash
git init
```

### 현재 상태 확인

```bash
git status
```

### 변경 파일을 스테이징 영역에 추가

```bash
git add .
```

### 변경 사항을 커밋으로 저장

```bash
git commit -m "프로젝트 초기 설정"
```

### 커밋 기록 확인

```bash
git log
```

이 단계까지는 GitHub 없이 Git만으로 실행할 수 있습니다.

---

## 8. GitHub 원격 저장소 연결

GitHub에서 빈 저장소를 만든 후 로컬 저장소와 연결합니다.

```bash
git remote add origin 원격저장소주소
```

연결된 원격 저장소를 확인합니다.

```bash
git remote -v
```

로컬 커밋을 GitHub에 업로드합니다.

```bash
git push -u origin main
```

각 부분의 의미는 다음과 같습니다.

| 항목 | 의미 |
|---|---|
| `git push` | 로컬 커밋을 원격 저장소로 전송 |
| `-u` | 현재 브랜치와 원격 브랜치의 연결 관계 저장 |
| `origin` | 원격 저장소의 기본 별칭 |
| `main` | 업로드할 브랜치 이름 |

---

## 9. 원격 저장소의 내용 가져오기

GitHub의 저장소를 처음 내려받을 때는 `clone`을 사용합니다.

```bash
git clone 원격저장소주소
```

이미 내려받은 저장소에서 최신 변경 사항을 가져올 때는 `pull`을 사용합니다.

```bash
git pull origin main
```

원격 저장소의 변경 이력만 확인하고 자동으로 병합하지 않으려면 `fetch`를 사용할 수 있습니다.

```bash
git fetch origin
```

---

## 10. Push와 Pull

### Push

로컬 저장소의 커밋을 GitHub 원격 저장소로 업로드합니다.

```text
로컬 Git 저장소 → GitHub
```

```bash
git push origin main
```

### Pull

GitHub 원격 저장소의 변경 내용을 로컬 저장소로 가져와 현재 브랜치에 반영합니다.

```text
GitHub → 로컬 Git 저장소
```

```bash
git pull origin main
```

---

## 11. Pull Request

Pull Request는 자신이 수정한 코드를 프로젝트의 기본 브랜치에 반영해 달라고 요청하는 기능입니다.

일반적인 과정은 다음과 같습니다.

```text
새 브랜치 생성
      ↓
코드 수정
      ↓
커밋
      ↓
GitHub에 Push
      ↓
Pull Request 생성
      ↓
코드 리뷰
      ↓
Merge
```

Pull Request를 사용하면 팀원이 변경 내용을 검토하고 의견을 남긴 후 코드를 병합할 수 있습니다.

---

## 12. 전체 작업 예시

```bash
# Git 저장소 초기화
git init

# 변경 상태 확인
git status

# 모든 변경 파일 추가
git add .

# 로컬 저장소에 커밋
git commit -m "첫 번째 커밋"

# GitHub 원격 저장소 연결
git remote add origin 원격저장소주소

# 기본 브랜치 이름 설정
git branch -M main

# GitHub에 업로드
git push -u origin main
```

---

## 핵심 요약

- Git은 로컬에서 파일의 변경 이력을 관리합니다.
- GitHub은 Git 저장소를 원격으로 저장하고 공유합니다.
- `git commit`은 로컬 저장소에 기록합니다.
- `git push`는 로컬 커밋을 GitHub에 업로드합니다.
- `git pull`은 GitHub의 변경 내용을 로컬로 가져옵니다.
- Pull Request는 코드 반영과 리뷰를 요청하는 GitHub 기능입니다.
- Git은 GitHub 없이도 사용할 수 있지만 GitHub은 내부적으로 Git 저장소를 활용합니다.
